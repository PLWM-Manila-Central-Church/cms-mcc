## Source-paper audit

- The thesis title is **A Web-Based Church Management System of Philippine Life Word Mission – Manila Central Church**. The Conceptual Framework section names the **Input–Process–Output (IPO)** model. The methodology also captions Figure 3 as a **HIPO Diagram**; visual inspection of the embedded image confirms a hierarchy of eight modules and their subfunctions. The two labels describe different artifacts and should remain distinct.
- The five study objectives are: (1) design/develop barcode-based attendance, event scheduling and notifications, a centralized member/finance/inventory database, automated reports, and RBAC; (2) implement the stated Node.js, React.js, MySQL, and RBAC stack; (3) conduct unit and system testing; (4) evaluate with an adapted ISO 25010 instrument; and (5) prepare a church deployment plan.
- The stated modules are attendance, member profiles, online pre-registration for services/events, event management, notification tools, finance, inventory, reports, and digital records archive. The thesis assigns full configuration/report control to Administrators; decision-support access to leaders and Pastors; operational entry to Staff/Volunteers; and profile, registration, attendance, and own-giving views to Members. The isolated QA role table has System Admin, Pastor, Registration Team, Finance Team, Cell Group Leader, Group Leader, unified Leader, and Member, but no generic Staff/Volunteer role. Map the prose to those specialized roles in the manuscript or get researcher/panel confirmation before adding a broad new role.
- The study scope is the Manila Central Church main branch and basic finance. It excludes multi-branch administration, advanced accounting/tax/forecasting, payroll, and advanced HR. Keep these limits explicit in the code and release review.
- The thesis says MySQL, while this project connects to TiDB Cloud through its MySQL-compatible protocol. This is an implementation/documentation mismatch, not evidence that the deployed database is MySQL Server. The researcher/panel should update the manuscript wording or choose a database migration before claiming the products are identical.
- The manuscript says Members can log attendance through barcode scanning. The agreed operating flow is member fixed QR → direct Registration scan, or leader batch QR → Registration review/approval. If “member logs attendance” was intended to mean self-check-in without Registration, that requirement needs researcher/panel clarification; do not silently weaken the existing check-in controls.

### 2. Repair the gaps found in the code audit

#### APR finding and repair sequence: archive access, downloads, and versions

**Analyze:** archive record detail currently has a visibility check, but the version and access-log subroutes do not apply that role policy. Access logs contain other readers' identity data and the UI only exposes them to users with the archive update/approve permission. The generic archive-file route checks only `archives:read`, so a role could bypass the row's `restricted`/`confidential` visibility if it obtains a file path. `ArchivesPage` builds file URLs with an environment-dependent absolute prefix and a `localhost:5000` fallback instead of using the configured API client path. The archive schema already has `current_version_id`, but the model omits it and create/update do not set it; file/version writes are separate transactions. Soft deletion removes the current physical file while leaving older version objects and rows behind.

**Plan:** centralize the visibility rule and apply it to detail, versions, access logs, and stored-file reads; require both archive read and update/approve permissions to read access logs; add record/version ID-based download endpoints; use the authenticated API client for file fetches and log actual view/download actions; map and update `current_version_id` with transactional version writes; retain stored objects on soft delete so the version chain remains consistent. Add focused automated tests for access policy and pointer/version behavior, then verify the same paths in the QA browser.
